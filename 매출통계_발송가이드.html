1전체 흐름

Admin_stat은 관리자 화면에 Selenium으로 로그인해서 세션 쿠키를 얻고, 그 쿠키로 관리자 내부 API를 직접 호출합니다. 매출 숫자는 관리자 서버의 salesStatsGrid 쿼리가 계산하고, Admin_stat은 결과를 표로 꾸며 메일로 보내기만 합니다.

1. 실행GitHub Actions(월요일 주간 · 1일 월간) 또는 로컬 수동 실행
2. 로그인Selenium으로 B2C·B2B 관리자 로그인, 쿠키 확보
3. API 호출/statistics/salesStatsGrid.do
4. 쿼리Statistics.xml salesStatsGrid
5. 메일 조립B2C·B2B 표 HTML + B2B 몰별 엑셀
6. 발송SMTP(STARTTLS)로 수신자에게
구분위치역할
매출 계산pobaonuri/11.business/resources/biz/app/statistics/Statistics.xml (salesStatsGrid)매출·주문수·구매자·재구매 지표 계산
수집·발송admin_stat/main.py로그인, API 호출, 엑셀 다운로드, 메일 발송
메일 본문admin_stat/report/sales.py표 HTML 생성, 엑셀 첨부
스케줄.github/workflows/admin_stat.yml월요일 주간(--sales-weekly), 매월 1일 월간(--sales-monthly) 매출 메일 발송. 현재 자동 실행은 주석 처리

2실행 방법과 스케줄

자동 실행 (GitHub Actions)

워크플로 드림몰 Admin 통계(.github/workflows/admin_stat.yml)가 admin_stat/ 폴더 안에서 매출 통계 메일만 보냅니다. 일일 Admin 리포트는 보내지 않습니다.

메일실행 시각실행 명령집계 기간
주간 매출 통계매주 월요일 09:02 KST (2 0 * * 1)python main.py --sales-weekly직전 주 월요일 ~ 일요일
월간 매출 통계매월 1일 09:02 KST (2 0 1 * *)python main.py --sales-monthly직전 달 1일 ~ 말일

1일이 월요일이면 두 번 실행되어 주간·월간 두 통이 모두 나갑니다.

현재는 자동 실행을 꺼 둔 상태 admin_stat.yml의 schedule이 주석 처리돼 있어 정해진 시각에 돌지 않습니다. 다시 쓰려면 schedule 주석을 풉니다. 지금은 Actions 화면의 Run workflow에서 weekly / monthly를 골라 수동으로만 실행할 수 있습니다.

옵션 없이 python main.py만 실행하면 일일 Admin 리포트(이메일·카카오톡)를 보내고, 실행한 날이 월요일이면 주간, 1일이면 월간 매출 메일을 함께 보냅니다. 워크플로는 이 방식을 쓰지 않습니다.

로컬 수동 실행

admin_stat/ 폴더로 이동한 뒤 실행합니다. 레포 루트의 main.py는 UI 테스트용이라 다른 프로그램입니다.

cd admin_stat

# 매출 통계 메일만 보내기 (일일 리포트는 건너뜀)
python main.py --sales-weekly
python main.py --sales-monthly

# 로그인 과정과 API 응답을 자세히 출력
python main.py --sales-weekly --debug

# 브라우저 창을 띄워서 로그인 과정 보기 (headless 해제)
python main.py --sales-weekly --show

필요 패키지: pip install -r requirements.txt (selenium, webdriver-manager, beautifulsoup4, python-dotenv, tabulate, matplotlib, openpyxl). 코드에서 requests도 쓰는데 requirements에는 빠져 있어서, 새 환경이면 따로 설치해야 할 수 있습니다.

3환경 변수

로컬은 admin_stat/.env, GitHub Actions는 저장소 Secrets에 같은 이름, 같은 값으로 넣습니다. .env는 .gitignore에 들어 있어 커밋되지 않습니다. 같은 레포의 UI 테스트 Secrets(ID, PASSWORD, WEBHOOK_URL)와 이름이 겹치지 않습니다.

EMAIL_FROM, EMAIL_PASSWORD보내는 계정, 앱 비밀번호Gmail은 Google 계정 > 보안 > 앱 비밀번호
EMAIL_SMTP_HOST, EMAIL_SMTP_PORTSMTP 서버기본값 smtp.gmail.com / 587. 네이버는 smtp.naver.com
SALES_EMAIL_TO매출 통계 메일 수신자쉼표로 여러 명. 비어 있으면 EMAIL_TO를 사용

5매출 통계 쿼리 구조

쿼리는 Statistics.xml의 salesStatsGrid 하나이고, 여러 WITH절(CTE)을 단계별로 쌓아 마지막에 합칩니다.

유효 주문 기준

모든 단계에 같은 조건이 걸립니다.

ORDER_BASE.DATA_STAT_CD = '01'
AND ORDER_BASE.ORD_STAT_CD = '20'
AND ORDER_DETAIL.RMN_ORD_QTY > 0        -- 전량 취소된 상품 라인 제외
AND ORD_ACPT_DTM BETWEEN 시작일 AND 종료일   -- 주문 접수일 기준
사이트 판별은 회원 기준 주문 등록 로직 버그로 ORDER_BASE.ST_ID가 항상 1로 저장됩니다. 그래서 B2C/B2B 구분은 주문한 회원의 MEMBER_BASE.ST_ID로 합니다.
gbCd대상 회원
B2CMEMBER_BASE.ST_ID = 1
B2B_TOTAL사이트 필터 없음. 해당 관리자 DB의 전체 회원
B2B_SITEstId를 주면 그 사이트만, 비우면 사이트별로 한 줄씩

단계별 흐름

CTE하는 일
VALID_ORDERS유효 주문과 회원, 매체(PC/MOBILE/기타)를 뽑습니다. 기간 제한 없이 전체 이력입니다.
RANKED회원별 주문 순번 CUM_SEQ를 매깁니다. 누적 재구매 판단용입니다.
MEMBER_PERIOD기간 × 매체 × 회원별로 기간 내 주문 수와 최대 순번을 집계합니다.
MEMBER_PERIOD_TOTAL위와 같지만 매체를 합친 버전입니다(합계 행용).
CHANNEL_STAT구매자 수, 기간 내 재구매자 수, 누적 재구매자 수를 매체별·합계로 셉니다.
SALE_STAT_SRC상품 라인별 매출과 수수료를 계산합니다(아래 식).
SALE_STAT매출·수수료를 SUM하고 주문 수를 COUNT(DISTINCT ORD_NO)로 셉니다.
PERIOD_LIST주문이 없는 기간도 0으로 나오도록 기간 목록을 만듭니다. 주는 월요일 시작(TRUNC(...,'IW'))입니다.
MEMBER_CUM각 기간 말일 기준 누적 회원 수(탈퇴 60 제외)를 구합니다.
최종 SELECT기간 × (PC / MOBILE / 합계)를 뼈대로 놓고 위 결과를 LEFT JOIN합니다.

매출 계산식

D.SALE_AMT * (D.RMN_ORD_QTY - D.RTN_QTY) AS SALE_AMT   -- 판매단가 × (잔여수량 - 반품수량)
D.CMS      * (D.RMN_ORD_QTY - D.RTN_QTY) AS CMS        -- 수수료단가 × 유효수량
2026-09 수정 내용 예전에는 수량을 곱하지 않아 2개 이상 산 주문이 적게 집계됐습니다. 커밋 61ab4139에서 수량을 곱하도록 고쳤습니다. 옵션가는 실제 결제에도 포함되지 않아서 더하지 않는 게 맞습니다(실 결제금액과 대조해 확인).

비율은 API가 0~1 소수로 주고, 메일에서는 ×100 해서 소수점 둘째 자리 %로 표시합니다. 0이나 값이 없는 금액·건수는 -로 표시합니다.

7메일 구성과 발송

항목내용
제목[온누리몰] 주간 매출 통계 - 2026년 11월 10일~11월 16일 형식
본문인사말 → B2C(온누리몰) 표 → B2B 통합 표 → 재구매 지표 각주 → 서명. 합계 행은 굵게, 노란 배경
첨부B2B 관리자에서 받은 몰별 엑셀 B2B_매출통계_YYYYMMDD.xlsx (받기 실패하면 첨부 없이 발송)
수신자SALES_EMAIL_TO, 없으면 EMAIL_TO
발송 방식smtplib로 SMTP 접속 → STARTTLS → 로그인 → 발송. MIME은 multipart/mixed(HTML + 엑셀)

코드 위치

  • 표 HTML, 인사말, 서명, 각주 문구: admin_stat/report/sales.py의 build_sales_email_html(), _FOOTNOTES
  • 컬럼 순서와 이름: admin_stat/report/sales.py의 COLUMNS, _KEY_MAP
  • 제목, 수신자, SMTP 발송: admin_stat/main.py의 send_sales_report()
  • 집계 기간 계산: admin_stat/main.py의 _sales_period()

admin_stat/report/sales.py에 있는 build_b2b_excel()은 지금 쓰이지 않습니다. 엑셀은 직접 만들지 않고 관리자 서버에서 내려받습니다.

8주의사항

PC + MOBILE ≠ 합계일 수 있음 주문 매체가 PC·MOBILE이 아니면 '기타'로 분류되는데, 결과 행에는 PC/MOBILE/합계만 있어서 기타 주문은 합계에만 들어갑니다.
B2B 몰별 엑셀에 B2C 사이트 행이 섞일 수 있음 B2B_SITE에서 stId를 비우면 사이트 필터가 걸리지 않고, 사이트 목록(ST_STD_INFO)에 ST_ID=1(B2C)도 포함됩니다. 쿼리 주석의 "ST_ID≠1"과 실제 동작이 다릅니다. 같은 쿼리를 쓰는 B2B 관리자 DB에 ST_ID=1 사이트가 있다면 첨부 엑셀에도 그 시트가 생깁니다.
매출은 할인 전 판매금액 기준 쿠폰·포인트·결제 할인을 빼지 않습니다. 정산 화면이나 실 입금액과 비교할 때 차이가 날 수 있습니다.
  • B2C·B2B 데이터가 둘 다 비면 그 주기의 메일은 보내지 않고 건너뜁니다.
  • B2B 로그인에 실패하면 B2B 표와 엑셀 없이 B2C만 보냅니다. 로그에 [B2B] 로그인 실패가 찍힙니다.
  • 집계 기간 계산은 KST 기준입니다. GitHub Actions cron은 UTC라서, 날짜가 KST와 같아지도록 09:02 KST(00:02 UTC)에 실행합니다. 08:02 KST로 두면 1일 실행이 UTC로는 전달 말일이 되어 cron으로 표현할 수 없습니다.
  • B2C 관리자 접속에 VPN이 필요한 환경이면, GitHub Actions에서는 접속이 안 될 수 있습니다.

9문제 해결

증상확인할 것
로그인 폼 필드를 찾지 못했습니다로그인 페이지 input name이 바뀌었는지 --debug로 확인하고 LOGIN_USER_FIELD/LOGIN_PASS_FIELD를 지정
로그인 실패계정·비밀번호, VPN 연결, 관리자 계정 잠금 여부
[매출통계] API 실패 또는 응답 행 수 0세션 쿠키 만료, Referer 헤더, 관리자 화면에서 같은 기간으로 직접 조회해 데이터가 있는지
[B2B] 엑셀 다운로드 실패 — Content-Type: text/htmlB2B 세션이 끊겨 로그인 페이지가 내려온 경우. B2B 계정과 로그인 로그 확인
이메일 발송 실패앱 비밀번호, SMTP 호스트·포트(587/STARTTLS), 보내는 계정의 외부 SMTP 허용 여부
메일 숫자가 관리자 화면과 다름같은 gbCd·기간·periodType으로 조회했는지. 화면 기본 조건과 스크립트 조건이 다르면 결과가 다릅니다
